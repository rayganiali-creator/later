# راهنمای کار بدون Claude — «بعداً» (Later)

این فایل برای وقتی است که خودت می‌خواهی برنامه را بسازی، به‌روز کنی و منتشر کنی.
همه‌چیز در این مخزن است؛ فقط به یک حساب GitHub و حساب توسعه‌دهنده‌ی بازار نیاز داری.

## ۱) چیزهایی که باید همیشه یک نسخه‌ی پشتیبان جدا داشته باشی
بدون این‌ها نمی‌توانی «به‌روزرسانی» همین برنامه را منتشر کنی:

1. فایل امضا: `later-release.jks`
2. رمز فایل امضا (`LATER_KEYSTORE_PASSWORD`)، نام کلید (`LATER_KEY_ALIAS`، معمولاً `later`) و رمز کلید (`LATER_KEY_PASSWORD`)
3. `LATER_PRO_SIGNING_KEY` — رشته‌ی تصادفی بلند. **باید همیشه همان بماند**، وگرنه Proِ ذخیره‌شده در پشتیبان‌های کاربرها معتبر نمی‌ماند.
4. `BAZAAR_RSA_KEY` — کلید عمومی RSA از پنل بازار (بخش پرداخت درون‌برنامه‌ای)
5. یک زیپ از کل کد (GitHub: Code > Download ZIP)

اگر فایل امضا را گم کنی، بازار اجازه نمی‌دهد نسخه‌ی جدید روی همین برنامه منتشر شود.
(بازار و گوگل راه‌هایی برای «ریست کلید» دارند، ولی لازم است با پشتیبانی تماس بگیری.)

## ۲) این‌ها در GitHub Secrets هستند (نه داخل کد)
مسیر: Settings → Secrets and variables → Actions

| نام | چیست |
|---|---|
| `LATER_KEYSTORE_BASE64` | فایل jks به‌صورت base64 (`base64 -w0 later-release.jks`) |
| `LATER_KEYSTORE_PASSWORD` | رمز فایل |
| `LATER_KEY_ALIAS` | نام کلید |
| `LATER_KEY_PASSWORD` | رمز کلید |
| `LATER_PRO_SIGNING_KEY` | کلید امضای Pro (ثابت بماند) |
| `BAZAAR_RSA_KEY` | کلید RSA بازار |

## ۳) ساخت نسخه‌ی اصلی (برای بازار)
فایل `.github/workflows/release.yml`.

**روش الف — با commit:** هر commit که در متنش `[release]` باشد و روی شاخه‌ی `claude/stoic-hawking-q8lh1i` push شود، ساخت را شروع می‌کند.

**روش ب — دکمه‌ی دستی:** Actions → «Release (signed store build)» → Run workflow.
این دکمه فقط وقتی دیده می‌شود که فایل workflow روی شاخه‌ی پیش‌فرض (`main`) هم باشد.
الان کدها روی شاخه‌ی `claude/stoic-hawking-q8lh1i` هستند و `main` خالی است. اگر می‌خواهی دکمه را داشته باشی:
شاخه‌ی `claude/stoic-hawking-q8lh1i` را با Pull Request در `main` ادغام کن، بعد در `release.yml` خط `push: branches:` را به `main` تغییر بده.

بعد از ساخت (۱۰ تا ۱۵ دقیقه):
- در همان اجرا، پایین صفحه بخش Artifacts → `later-store-release`
- داخلش: `app-store-release.aab` (برای بازار) و `app-store-release.apk`
- فایل‌ها ۱۴ روز می‌مانند؛ همان موقع دانلودشان کن.

## ۴) به‌روزرسانی نسخه
در `pubspec.yaml` خط `version:`
مثلاً `1.1.0+2`: بخش قبل از `+` نام نسخه است و بعد از `+` **کد نسخه**.
کد نسخه باید برای هر آپلود **بزرگ‌تر** از قبلی باشد (مثلاً `1.1.1+3`).

## ۵) فایل‌های مهم
| کار | فایل |
|---|---|
| قیمت و مدت پلن‌های Pro | `lib/core/config/pro_plans.dart` |
| محصولات بازار (مصرفی/consumable) | `later_pro_1m`، `later_pro_3m`، `later_pro_6m` |
| ایمیل پشتیبانی و نسخه‌ی قوانین | `lib/core/config/app_config.dart` |
| متن قوانین و حریم خصوصی | `assets/legal/` و `docs/privacy/` |
| متن‌های برنامه (فارسی/انگلیسی) | `tool/gen_arb.py` بعد `flutter gen-l10n` |
| توضیح فروشگاه | `store/LISTING_fa.md` |
| راهنمای تست دستی | `docs/TEST_PLAN.md` |
| معماری و امنیت | `docs/ARCHITECTURE.md` و `docs/SECURITY.md` |

اگر متن قوانین را عوض کردی، `termsVersion` / `privacyVersion` را یکی بالا ببر تا از کاربرها دوباره تأیید بگیرد.

## ۶) خریدهای Pro و بازیابی
- خریدها بعد از فعال‌شدن **مصرف نمی‌شوند**؛ بازار نگهشان می‌دارد و برنامه Pro را از روی آن‌ها دوباره می‌سازد.
  به همین دلیل بعد از نصب دوباره یا گوشی جدید، Pro خودش برمی‌گردد (و دکمه‌ی «بازیابی خرید» هم هست).
- بازار فروش دوباره‌ی همان محصول را تا وقتی هنوز مالک آن است نمی‌پذیرد؛ برنامه این حالت را با پیام «این پلن را قبلاً خریده‌ای» نشان می‌دهد.
- خریدهای نسخه‌های قدیمی (قبل از ۱.۱.۰) بازیابی نمی‌شوند.
- بازیابی واقعی را فقط با نسخه‌ی امضاشده‌ی فروشگاه می‌شود امتحان کرد (راهنما: انتهای `docs/TEST_PLAN.md`).

## ۷) اگر CI قرمز شد
- ابتدا لاگ را باز کن (Actions → اجرا → کار قرمز).
- «No space left on device» یا «Timeout waiting for emulator to boot» از ماشین GitHub است، نه از کد: «Re-run failed jobs» را بزن.
- در مخزن عمومی دقیقه‌ی اجرا رایگان است. اگر مخزن را خصوصی کنی، سهمیه‌ی ماهانه دارد و تست شبیه‌ساز (که ۴ نسخه‌ی اندروید را اجرا می‌کند) سنگین است؛ در `.github/workflows/emulator.yml` می‌توانی `api: [31, 33, 34, 35]` را کم کنی.
- تست محلی: `flutter analyze` و `flutter test`

## ۸) نسخه‌ی تست (QA)
هر push یک نسخه‌ی تست با ابزارهای QA (شبیه‌سازی Pro، سفر در زمان، داده‌ی نمونه) می‌سازد:
GitHub → Releases → جدیدترین `qa-N`. با پکیج `app.baadan.later.qa` کنار نسخه‌ی اصلی نصب می‌شود.

## ۹) امنیت
- نسخه‌ی فروشگاه اجازه‌ی اینترنت ندارد؛ داده‌ها فقط روی گوشی می‌مانند.
- هیچ کلید یا رمزی داخل کد نیست؛ کل تاریخچه یک بار بررسی شده است. قبل از commit مطمئن شو فایل‌های `*.jks`، `key.properties` و رمزها اضافه نشوند (CI هم این را چک می‌کند).
- مخزن عمومی است؛ جزئیات و محدودیت‌ها در `docs/SECURITY.md`.
